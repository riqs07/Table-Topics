# Architecture Decisions

**Purpose:** Record why each technology was chosen, so a reader can challenge it.
**Last updated:** 2026-10-15

| # | Decision | Why | Revisit when |
|---|----------|-----|--------------|
| 1 | **Next.js with TypeScript** | API routes keep the AI key off the device; one codebase scales into a product | We outgrow serverless routes |
| 2 | **Installable web app (PWA), no native app** | Works on a phone, no app store, fastest to ship | Users ask for reminders iOS web cannot deliver |
| 3 | **Local-first storage (IndexedDB), no accounts** | Privacy matters for a vulnerable activity; no backend to run | Users want sync across devices |
| 4 | **Web Speech API for live transcript, Whisper as fallback** (provisional until spike C5) | Live words on screen feel good and cost nothing; Whisper covers unsupported browsers and later gives word timestamps | Web Speech accuracy proves too low |
| 5 | **Metrics from transcript only** | We only show numbers we can compute reliably | Audio analysis is added for tone and pitch |
| 6 | **Claude Sonnet for session feedback, Claude Opus for weekly summaries** (M6: `claude-sonnet-5-5` at medium effort, `claude-opus-5-5` for summaries; set in `src/config/models.ts`) | Sonnet is fast and cheap for short transcripts; Opus was chosen for the weekly view. Likely overkill, so measure it | Weekly summary quality shows no gain over Sonnet |
| 7 | **Model names live in one config file** | Models change; one edit updates everything | Always |
| 8 | **Access passphrase, rate limits, and a provider-side spend limit on every AI route** | A deployed route is public, and counters in server memory do not hold up on serverless hosting, so they need a small shared store | Usage grows past one user |
| 9 | **Vitest, Testing Library, Playwright** | Fast unit tests for logic, component tests for screens, a few end-to-end checks of the full loop | Tests become slow or flaky |
| 10 | **Hosting on Vercel** | Zero-config for Next.js, free tier suits one user | Costs or limits change |
| 11 | **All colors, fonts, and spacing live in theme files; components use named roles only** | You control the look, and a palette change is one file (see design/design-system.md) | Never; this is a principle |
| 12 | **Test the riskiest assumptions first with throwaway spikes on a real phone** | Transcription behavior (risks R1 to R3) can reshape the architecture, so we learn it before building on it | Spike results arrive (C5) |
| 13 | **Pinned tool versions: TypeScript 6.0, ESLint 9, Node 22+, pnpm 10** (added 2026-10-12, M0) | TypeScript 7 and ESLint 10 are out, but the Next.js lint rules do not support them yet. Exact versions plus the lockfile keep builds repeatable (R12) | The Next.js lint config supports TypeScript 7 and ESLint 10 |
| 14 | **Coach feedback uses structured output (a JSON schema), the standing instructions are cached, and no automatic model fallback** (added 2026-10-13, M6) | The schema guarantees keep / change / retry cue every time; caching cuts repeat input cost. Server-side fallback on this model only retries cyber and AI-development declines, which speech practice will not trigger, so a decline is shown plainly instead | Declines show up in real use |
| 15 | **Limits: 6 feedback calls a minute, 60 a day, counted in Upstash Redis; if the counter is down, feedback pauses** (added 2026-10-13, M6) | About a cent a session caps the worst day near $0.60, on top of the provider spend limit. Failing closed means an outage can never lift the cap | Real use needs more |
| 16 | **A small hand-written service worker instead of a PWA plugin** (added 2026-10-13, M10) | About 100 lines, fully tested, no extra dependency to keep up to date; it only needs to save a handful of pages and their files | Offline needs grow (background sync, push reminders) |
| 32 | **Recordings are deleted after listening back unless the user keeps them** (added 2026-10-17) | The user asked for the listen-back step to offer saving the recording for comparison and to discard it otherwise. Once the notes are saved (or skipped), an unkept recording is deleted and the session's audio key cleared (the session is saved first, so it never points at missing audio); the transcript, numbers, word times and notes stay. Off by default. The first recording is always kept, since progress is measured against it. Retries and sessions from before the step have no listen-back step, so they still follow the "keep the last N" setting | People regret losing recordings, or want to keep or delete one later from its page |
| 31 | **The coach reads the user's notes only if they switch it on, and feedback then waits for the notes** (added 2026-10-16) | Notes are personal, so sharing them is a choice in Settings ("Let the coach read my notes"), off by default, stored in the settings record. When it is on, a new first try's feedback request waits until the notes are saved (the request says "awaiting notes" and the session page asks again once they are), so the coach can answer them. Notes go to the server only then, capped at 500 characters each and 12 tags, fenced as data in the coach's message with tags turned into their words and unknown tags dropped, and with an instruction that they are not instructions | People want the coach to read notes without waiting, or notes prove a route for prompt injection |
| 30 | **Listen back and write your own notes before the feedback opens** (added 2026-10-16) | Judging your own recording before seeing the numbers builds the skill of hearing yourself, and a note in your own words is a better cue for the next try. The user chose to make listening the default: a new first try (marked by `selfReview: null`) shows the listening step first, and saving opens once nearly every second has been played (long recordings: the first and last 45 seconds). "Skip this time" keeps the loop from becoming a chore. Retries and older sessions skip the step. Feedback is still requested in the background, and saving it now re-reads the session so notes saved meanwhile are kept | People skip most of the time, or say the step slows them down |
| 29 | **Crutch words count only where they act as fillers; a reading counts only words added to its text** (added 2026-10-16) | C7 counted every crutch word everywhere and said to trim if numbers looked inflated. They did: "so conceived and so dedicated" made a Gettysburg reading score 4.3 fillers a minute, and "I really like it" counted twice. Now hesitation sounds, hedging phrases and words that are almost always fillers (basically, literally, honestly, anyway, whatever, okay, yeah, kinda, sorta) always count. Words that are also ordinary (like, so, well, just, really, actually, totally, seriously, right) count only when they open a sentence, sit next to another filler, are said twice in a row, or, for "like", do not follow a word that makes it a verb or comparison ("I like", "feels like"). With text on screen (readings, lessons, rehearsals), words that are part of the text never count and any filler added to it does; a rehearsal is measured against the full talk whatever the memory rung. The coach gets the same number. Rules live in `src/core/fillers.ts` | People report fillers the count misses, or ordinary words still counted |
| 28 | **Word times come from when each word first appears in the live transcript, measured on the device** (added 2026-10-16) | The browser's speech service gives no word timings, and a paid transcription service would cost money and send audio off the device. Every time words arrive, the app notes when each word position first appeared and, with text on screen, when each word of the text was first read (`src/core/liveReading.ts`), following the reader with a short look-ahead so skipped words and fillers do not lose the place, and needing two words in a row to jump further. The times are approximate (the service runs a little behind and sends words in bursts), so findings compare stretches rather than single words: pace in the first third of the time against the last third (a change of 15% or more is named), and a pause at a mark counts when the gap is at least 0.8 seconds (`src/core/wordTiming.ts`). Times are saved to a tenth of a second on the session; older sessions simply show neither finding. The same following drives the live highlighting | A real phone shows the service's bursts make pace or pause findings wrong, or word timings become available from a service we already use |
| 27 | **Flat square cards for choices, finishing option B** (added 2026-10-16) | Option B's last stage relaxes the "no cards" rule from the first design: long ruled lists of modes and speeches read as one block, and people could not see where one choice ended. Cards stay within the script-page look: square corners, a hairline edge, the plain paper, no shadow, no rounding. They are used only where a page offers a set of choices (the Practice modes, the famous speeches); lessons, passages and history stay as rows. Option B as a whole shipped in five stages: navigation and tap targets, the recording stage, the results page, visible progress, and these cards | Pages start filling with cards that are not choices, or the cards make phone pages much longer |
| 26 | **A warmer, more app-like interface on the script page (option B), built in stages** (added 2026-10-16) | A UI audit found the main action often below the fold on a phone, almost every tap target 23 to 24 pixels against the 44-pixel guideline, four different looks for "start", long flat lists, a recording state that looked like the start state, and feedback buried below caveats. The user chose option B: keep the serif, the paper, and the forest green, but add a phone tab bar, a sticky main action, 44-pixel targets with one primary and one secondary style, a full-screen recording stage, a results card that leads with the one fix, and visible progress. Stage 1 (navigation, sticky action, tap targets) shipped first. The "no cards, no widgets" rule will be relaxed where later stages need it, and the design system says so when they do | Real use on a phone shows the tab bar or sticky band getting in the way |
| 25 | **Organise the app around three jobs, with one recommended next step** (added 2026-10-15) | Eight modes had grown, and three of them could only be found in a small "More" line on the home page. The user chose a menu by job (Today, Talks, Practice, Skills), a Today page that recommends one next step, a one-question welcome, a "How this works" note on every mode, and plainer names. Every mode's description lives once in `src/content/modes.ts`; the recommendation is `src/core/nextStep.ts`. Lessons and the library merged into Skills; their old addresses redirect. This supersedes the home-screen layout approved with the wireframes at C11 | People cannot find a mode, or the recommendation is ignored |
| 24 | **Q&A practice: questions from the transcript only, a one-minute answer, one shared limit** (added 2026-10-15, plan step B3) | Questions are written from what was said in the run, never a rehearsal's script, which keeps decision 20. The question itself is sent with an answer's feedback request (at most 300 characters, fenced as data) because the coach cannot judge an answer without it. Answers aim for one minute rather than the Table Topic window the plan first named: real answers after a talk are short, and a minute is the usual advice. Questions and feedback count against the same daily limit, so the cost guard still holds. Typing your own questions needs no server, so the mode works without the coach | Answers prove too short to practise anything, or questions use up the daily limit |
| 23 | **Event prep plans each day from the date, with sections taken from blank lines** (added 2026-10-15, plan step B1) | The plan is worked out from the number of days left, so it adjusts itself when the date moves and needs nothing stored but the date. Phases run in a fixed order (sections, opening and close, whole run, keywords, memory), each getting an equal share of the days, with hand-picked short plans for two to five days. Sections come from blank lines because people already write talks in paragraphs; nothing extra to mark up. Defaults agreed with the user: plans reach 30 days ahead, no reminders | People want to mark sections themselves, or ask for reminders |
| 22 | **VoiceLab is for public speaking: the target user is someone who has to speak to an audience** (added 2026-10-15) | The user wants the app to be about public-speaking improvement, and most of what exists already serves a speaker: Table Topic, prepared responses, read aloud, the pause drill, Rehearse my talk, and the skill path. The coach's instructions, the weekly focuses and some prompts still served the old target user (the shy person who wants to be more outgoing), so they change to match. The step-by-step plan is in plan-public-speaking.md | Real use shows people mainly want help with conversation rather than talks |
| 21 | **A skill path of open lessons, each a practical tip, instead of levels to unlock** (added 2026-10-15) | The user wanted levels without gating: all lessons (ten, then sixteen from 2026-10-15) are open from the start and can be repeated. Each pairs one tip with a text and a check the app can already make on the device; skills that need judgement (stress, signposting, the rule of three) wait for the coach rather than getting a guessed number. Tongue twisters are one lesson, not the path. The practice library replaces the daily read-aloud band | Users want a sense of progression (then add a "practised" mark or best result per lesson), or the checks prove unreliable on real voices |
| 20 | **Pauses come from the loudness readings, measured on the device; a rehearsal's script never leaves it** (added 2026-10-15) | The level meter already reads loudness ten times a second, so saving those readings costs little and needs no service. Silence is judged against the speaker's own loudness, so quiet speakers are treated fairly. Without word timings the pause drill compares the number of pauses with the number of marks, not their exact places. Talks may be personal or confidential, so the coach is told it was a rehearsal but gets only the transcript | Word timings (Whisper or a similar service) become available, or rooms are too noisy for the threshold |
| 19 | **Reading checks and "then and now" run on the device; passages are public domain or written for the app** (added 2026-10-15) | Word-by-word alignment of transcript and text needs no service and costs nothing. A missed word may be the speech service mishearing, and the page says so. Speech excerpts are U.S. works from 1775 to 1963 (eighteen since 2026-10-16), either published before 1929 or given by a U.S. president in office (a government work), public domain or official presidential addresses; copyrighted books are not included. The coach receives a passage id, not its text, and looks the text up | Misheard words make the percentage misleading in practice, or the user wants to paste their own text (planned as "Rehearse my talk") |
| 18 | **Two modes for the MVP: Table Topic and Record Response** (added 2026-10-14) | Table Topic: a short briefing ("very little waiting time"), a light short-answer prompt, a 10-second countdown, then Toastmasters timing (1:00 to 2:00; green 1:00, yellow 1:30, red 2:00; under 1:00 or over 2:30 would not qualify). Record Response: a deeper prompt, 2 minutes to think (Ready starts early) with a fixed structure hint and two or three angles written for each prompt, then a 3:00 goal (yellow from 2:15, red past 3:00, stops at 4:00). These replace the one-minute session and the warm-up on the home screen; old sessions keep their labels. The baseline becomes the first Record Response. Accepted as good enough for the MVP, not final: the user does not want an exact copy of Toastmasters, so timings, countdowns, and hints will be tuned after launch (see roadmap, "To revisit after the MVP") | Daily use shows the timings or hints are wrong for a shy beginner, or the app feels like a Toastmasters clone |
| 17 | **Desktop recording: the browser's own speech recognition for the live transcript, MediaRecorder for the audio** (added 2026-10-13, M5, desktop first) | Free, no account, and live words on screen. The note before recording says words go to the browser's speech service (Google in Chrome, Apple in Safari) and the recording stays on the device. The phone approach is still decided at C5 | The phone test (C3) or filler accuracy (R1) says otherwise |

## Not chosen

- **A server database:** conflicts with the privacy goal and adds ops work.
- **Five-dimension scoring:** transcripts cannot support it honestly (see PRD section 5).
- **Azure Pronunciation Assessment for prosody (intonation, monotone, pause naturalness)** (considered 2026-10-13, skipped for now): scores against native-speaker delivery rather than confidence, sends audio to Microsoft, English (US) only, and needs another account. Revisit if on-device pitch and pause measures prove too weak.
- **Voice emotion APIs such as Hume:** inferring feelings from the voice is a guess presented as fact (PRD section 5).
